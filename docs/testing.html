KOReader Companion — testing

How this app is actually tested

Short version: there is no PHPUnit and no frontend test framework. Correctness is checked by static analysis, four PHP-version lints, a supply-chain audit — and, doing the real work, two hand-written Bash scripts that boot a genuine Nextcloud 34 container and hit its live HTTP API with curl. What follows is what each of those actually does, why the frontend has no component tests at all, and where the honest gaps are.

The direct answer

Frontend tests, or just the API?

Just the API — and not even that through a framework.

  • No frontend test exists. No Vitest, Jest, Cypress, Playwright, or Testing Library anywhere in package.json. Not one Vue component (LibraryView, SettingsView, ReaderModal, …) has ever been rendered or asserted on outside a real browser.
  • npm run lint exists but cannot run. It calls eslint src, but ESLint has no config file in this repo and is not even a direct devDependency — it is a transitive leftover pulled in by something else. Running it locally fails immediately with "ESLint couldn't find a configuration file." It is also never invoked in CI. Not a gap that is merely unwired — the script is dead weight.
  • What does exist is black-box HTTP testing against a real server. Two Bash scripts drive a genuinely running Nextcloud 34 + PostgreSQL stack over curl and check status codes, headers, and response bodies — the same way a real OPDS reader or a real KOReader device would. That is the entire correctness net for both the PHP backend and the parts of the frontend that talk to it (nothing checks the Vue rendering itself, only the API it calls).
  • Everything else is a gate, not a test in the sense of asserting behaviour: syntax lint, static analysis, dependency audits, a schema check, and a committed-bundle freshness check. Real and useful, but none of them execute the application's logic.

The map

Six CI jobs, one real test suite

Every push to main and every pull request runs .github/workflows/ci.yml. Five of the six jobs are gates; only integration executes the application.

The real test suite

How the integration job actually works

No test framework, no mocks, no fixtures database. A real container, real HTTP, real assertions on what comes back.

  1. Boot a real stack. docker compose up -d --wait --build app db starts Nextcloud 34.0.2 on Apache against PostgreSQL 17, and waits for both to report healthy. A third container, the cron sidecar, starts after — it is not required for the tests to run, since seeding drains the job queue itself (see below), and it deliberately carries no healthcheck of its own.
  2. Provision it. dev/provision.sh waits for the Nextcloud installer to finish, applies dev-only config, enables the app, sets up the admin user and the KOReader sync password, and uploads a handful of sample books over WebDAV — deliberate, since metadata extraction hangs off a real NodeCreatedEvent, which copying files into the data directory would never fire. It then drains the background job queue directly (php -f cron.php) so the books carry real extracted titles and authors by the time the suites run, rather than the placeholder filename a fresh upload starts with.
  3. Run two Bash scripts against it. test_scripts/test_opds.sh and test_scripts/test_koreader.sh, both plain #!/bin/bash with no framework underneath — a handful of shared shell functions or nothing at all. Each one authenticates the way a real client of that protocol would (HTTP Basic for OPDS, an MD5 header pair for KOReader sync) and asserts on the actual response: HTTP status code first, then content — an OPDS feed is parsed just enough to pull out one tag and confirm it is well-formed XML with the right profile=opds-catalog content type; a KOReader sync response is checked against the exact JSON shape the reference kosync server produces.

OPDS test_opds.sh

34/34 passed on the run that produced this page. Ten sections: authentication, core feeds, faceted browsing (author/series/genre/format/language), content-type validation, error handling, the auth handshake, input validation, book-specific endpoints, and category browsing by a real author found in the seeded library.

KOReader test_koreader.sh

17/17 passed on the same run. Seven sections: health check, authentication, the reading-progress API, error handling, real-device value edge cases (full float precision, long device names — added after those exact values once broke production), and content-type checks.

What one check actually looks like

There is no assertion library. A helper wraps curl, a status code is compared with a plain [[ ]], and the result is printed with a colored glyph:

# abridged from test_scripts/test_opds.sh
opds_request() {
  curl -s -u "$USERNAME:$PASSWORD" \
       -H "Accept: application/atom+xml;profile=opds-catalog" \
       "$OPDS_BASE_URL$2"
}

status=$(opds_request GET /authors -o /dev/null -w '%{http_code}')
if [[ "$status" == "200" ]]; then
  print_result "PASS" "Browse by Author"
  → ✓ Browse by Author
else
  print_result "FAIL" "Browse by Author" "HTTP $status"
  → ✗ Browse by Author  HTTP $status
fi

The other three gates

Static analysis, lint, and supply chain

Psalm — the closest thing to a unit test

Level 4 across lib/, with findUnusedCode="false" and a checked-in baseline. It reasons about types and reachability without running any code, so it catches a class of bug the integration suite structurally cannot: a wrong type flowing through a path no test happens to exercise. It cannot catch a wrong value — only Psalm would never have caught the reading-progress column being too narrow for a real device's float precision; the integration suite's real-device-value section exists specifically because static analysis cannot.

Four PHP versions, one purpose

8.2 is the floor this app declares support for; 8.5 is what the Nextcloud 34 container actually ships. Running php -l across the gap exists to catch exactly what it already has once: code that is silently fine on the floor version and starts deprecating on the newest one, long before an admin's server upgrade turns it into a production warning nobody asked for.

Supply chain: two real findings, days apart

This gate is not theoretical — it has already caught two real problems in this project, both from ordinary dependency drift rather than anything introduced on purpose:

Caught: composer.lock had pinned sebastian/diff to a version requiring PHP ≥8.4, because the lock had last been resolved on an 8.4+ machine. The 8.2/8.3 lint legs and Psalm died at composer install before ever reaching their actual check. Fixed by pinning config.platform.php to the declared floor and re-resolving, the same idea as npm's overrides below.
Caught: npm audit flagged five high-severity advisories against every @xmldom/xmldom release up to 0.8.12 — a transitive dependency of epubjs, the in-browser EPUB reader, which only reaches for it as a fallback when a browser has no native DOMParser (never true in this app's actual runtime, but the code still ships in the bundle, and EPUB files are attacker-controlled input by this project's own threat model). npm audit fix only offered a breaking major bump of epubjs itself; a package.json overrides entry pinned just the vulnerable transitive dependency to a patched release instead.

Being honest about it

What is not tested

None of this is hidden — it follows directly from what is listed above not existing.

No PHP unit tests. phpunit/phpunit is in composer.lock only as a transitive dependency of Psalm's own toolchain — it is never invoked, there is no phpunit.xml, and nothing under lib/ has ever been exercised in isolation. Every backend behaviour that is checked at all is checked through the integration suites, over real HTTP, against the whole stack — never a single class or method on its own.
No frontend tests of any kind. No Vue component has been mounted and asserted on outside a real browser; the historical record for frontend correctness in this project is manual — entries like "verified: real Chrome session, zero console errors" in the project's own task log, not an automated run anyone can repeat.
npm run lint is not merely unwired, it is broken. No ESLint config exists in this repository, and ESLint is not a direct dependency — running the script fails immediately with "couldn't find a configuration file."
No browser-driven end-to-end test. Nothing automates opening the app, clicking through the settings folder picker, uploading a book, or opening the reader. All of that is integration-tested only insofar as the HTTP endpoints it calls are.
Narrower gaps worth naming: CBR (RAR comic) cover extraction has never been exercised end-to-end for lack of a real fixture; performance numbers quoted in the project's own history are one-off manual measurements, not a benchmark that runs in CI; and the reading-position round trip against real KOReader hardware — as opposed to Readest and other EPUB readers used during development — remains unconfirmed.
