Security review · koreader_companion v1.4.0 · 11 Aug 2026

The injection bugs aren’t there. The denial-of-service is.

Reviewed for exposure on a public Nextcloud instance — untrusted registered users, plus anonymous internet traffic reaching /opds/* and /sync/*. On the classic vulnerability classes this code is better than most Nextcloud apps: every query is parameterised, file ownership is scoped through the user folder, and the new EPUB reader’s sandboxing is correct. The problem was somewhere less glamorous: nothing rate-limited anything, and several endpoints did unbounded work per request.

That has since been addressed — findings are kept in full below because the reasoning is the point, with each one’s current status marked. A second pass over v1.5.0 (the reader, the highlight list, the annotation endpoints) found one more amplification of the same family and closed it. What remains is two credentialed, bounded items, neither of which gates a deployment.

Honest correction on H1b. The structural claim holds — a download no longer costs work proportional to the library — but the measured win is smaller than the finding below implies, and the finding overstated the mechanism. Measured twice against the pre-fix commit, on the same running instance: 

                        feed          single download
307 identical fixtures  0.78 → 0.75s   0.84 → 0.79s   (~6%)
246 real books, 329 MB   0.78 → 0.75s   0.93 → 0.80s   (~13%)

Real books roughly double the download gain, which is the direction predicted — per-file parsing costs more when the files are not 300 copies of one small EPUB — but it is still 13%, not an order of magnitude. Feed timings are unchanged within noise in both runs. And the reconciliation walk already skipped unchanged files, so it was re-walking the directory tree on every request, not re-parsing every book as H1b claims below. The fix is worth having because the cost no longer scales with the library, not because of the wall-clock number today.

Verified on a live Nextcloud 34.0.2. OPDS 29/29 and KOReader 13/13. The M1 migration was proved on the real upgrade path: stored as a bare MD5, first sync authenticated via the legacy branch, and the value came back as $2y$12$… with all tests still green. Two KOReader failures seen mid-work turned out to be a dev-stack bug — provision.sh had been silently failing to set the sync password, because occ user:setting cannot overwrite a typed value and its exit code was ignored. Worth knowing: the suite's PUT progress update assertion passes on a 401 body, so it cannot tell working auth from broken auth. Not covered by any test: M5, M6 and L1 were verified by reading, not by running.

The one number that decides this

#[AnonRateLimit] and #[UserRateLimit] appear zero times in the codebase. Meanwhile a single sync request with an unrecognised document hash walks the entire library, opens every file, and logs about twelve lines per file:

0

Cost to the attacker: one HTTP request with a random 32-hex string. Repeat in a loop.

Second pass — v1.5.0, the annotation surface

One new amplification, found by measuring rather than reading

The reader, the highlight list and the annotation endpoints did not exist when the review above was written. Everything below was checked against a running instance; the numbers are measured, not estimated.

A1 Annotation lookup was linear in stray .json files — fixed Authenticated

AnnotationService resolved every .json in the library folder to a book before deciding whether it was wanted. A 32-hex name cost an indexed query; anything else cost a library-wide Folder::search(). Any user with stray JSON among their books — a Calibre export, their own notes — paid for it on every library page load, and /annotations/counts allows 120 per minute. 

13-book library, counts request       before     after
baseline, 1 annotation file          0.052 s    0.052 s
+ 150 stray .json files              0.260 s    0.054 s   (1.4 ms each, linear)
+ one 3.9 MB / 7451-record file      0.064 s    0.064 s   (caps already held)

Extrapolated, a thousand stray files meant 1.4 s per request — at 120 requests a minute, more than one worker saturated by one user.

Fixed: resolve the wanted names first, in two batched indexed queries, then read only files matching one. A file nobody asked about now costs a hash-map lookup. Requests are bounded to 500 ids at the controller and 250 books in the service.

H1a Unknown sync hashes no longer open the library — fixed Sync creds

The earlier fix bounded tryAutoIndex() to 200 files, but did not exclude books that already had a hash mapping — and indexing writes those mappings when it runs. So every unknown hash re-hashed the 200 most recently touched books for nothing. 

PUT /sync/syncs/progress    before     after
unknown (random) hash       0.34 s     0.257 s
known hash                  0.26 s     0.259 s   ← now identical

The delta was 6.5 ms per book on a 13-book library; at the 200-file cap that is ~1.3 s of file I/O per request, repeatable in a loop by anyone holding sync credentials. Fixed by making only unmapped rows candidates. Regression-checked: deleting a book’s mappings and syncing its real hash still finds it and recreates the mapping.

Cleared in this pass

Cross-user isolation, tested rather than reasoned about. A second account asking about another user’s book, by file id, on every endpoint that takes one: 

GET  /annotations/counts?ids=…   {"counts":[]}
GET  /books/{id}/annotations         {"annotations":[]}
GET  /books/{id}/progress            {"progress":null}
GET  /books/{id}/file                404
PUT  /books/{id}/metadata            412   (CSRF; ownership also scoped)
PUT  /books/{id}/progress            412
DELETE /books/{id}                   412

Readers and writers alike resolve through getUserFolder($uid)->getById($id), and the annotation name map is scoped by user_id in both queries, so another user’s id simply matches nothing.

Also re-verified: no v-html, innerHTML or document.write anywhere in src/, so annotation text and notes — attacker-authored, arriving from a file — are escaped by Vue on the way out. No SQL is built by concatenation; the one hand-written fragment (createFunction() for the “last updated” sort) is a static string reached only through an allow-listed switch. The reader’s sandbox still holds: allowScriptedContent: false, and the CSP widens blob: for frames, styles, fonts, images and media — never scripts. Annotation files are capped at 4 MB, 2000 records and JSON depth 8, and the 3.9 MB probe above shows those caps doing their job.

Finding 1 of 13 · High

H1 — Remote resource amplification, unthrottled

Three separate paths turn one cheap request into work proportional to the whole library. None of them is rate-limited, and two are reachable by an anonymous caller with valid OPDS credentials or a sync password.

H1a tryAutoIndex() scans and opens the entire library Anon + sync creds

KoreaderController.php:350-424. Fires on any PUT /sync/syncs/progress whose document hash is not already mapped. Iterates every book, calls getById() and fopen() per file, and hashes each one. Unknown hashes are also deliberately stored anyway (:168-170), so the attacker controls both the CPU cost and a growing table.

DocumentHashGenerator emits up to 12 logger->info calls per file — 21 of the 45 info-level calls in lib/ live in that one class. Log-disk exhaustion arrives before CPU exhaustion.

Fix: bound the scan (cap files per request, or move auto-indexing to a background job keyed by hash), and demote the per-offset logging to debug.

H1b Every listing re-scans and re-parses the whole folder Anon + OPDS creds

BookService::getBooks() → scanFolder() → extractMetadata() per file (BookService.php:63-98, 550-619). Runs on every OPDS feed, every facet feed and every web listing. getBookById() (:1216-1226) then does an O(library) linear scan over that result — used by bookFile, opds#download and opds#thumbnail, so a download costs a full library scan.

None of the 15 OPDS methods carries a rate-limit or brute-force attribute.

Fix: serve listings from oc_koreader_metadata and let the background job own extraction; look books up by id in SQL, not by scanning.

H1c batchRename holds a PHP worker for minutes Authenticated

SettingsController.php:98-136 renames the entire library synchronously inside the request, with usleep(500000) in the loop (:205). Half a second of deliberate sleep per chunk, in-request.

Fix: move to IJobList — the pattern ExtractMetadataJob already establishes.

Findings 2–7 · Medium

Credential design, auth boundaries, and hygiene

None of these is remotely exploitable on its own. Each one either widens the blast radius of a different compromise or removes a layer that should be there.

M1 The sync credential is an unsalted MD5 that is itself the verifier Blast radius

PageController.php:152 stores md5($password); KoreaderController.php:213 compares the wire value straight against it. The stored value is the credential, so anything that reads config — a database backup, a read primitive in any other installed app — yields a directly replayable secret and a trivially crackable password. Users reuse passwords; this one is one rainbow-table lookup from their Nextcloud account.

There is no server-side password policy: :146 checks only empty(), so a one-character sync password is accepted. The 4-character minimum lives only in the browser (ConnectionView.vue:40). FLAG_SENSITIVE (:159) does encrypt at rest, which genuinely helps, but does not change the design.

Fix: KOReader’s protocol mandates MD5 on the wire — that cannot change. What can: store password_hash() of the received MD5 and verify with password_verify(), and enforce a length floor server-side.

M2 setUser() driven by a request header on a public route Auth boundary

KoreaderController.php:221 and :364. On routes marked #[PublicPage], the app installs a session user chosen by the x-auth-user header and grants full filesystem context for the rest of the request. The MD5 check does gate it, so this is not an escalation today — but it makes every downstream bug in that request a bug that runs as someone else, and it mutates request-global state.

Related: getCurrentSyncUser() (:226-245) re-reads the same header and trusts it without re-verifying the key. Safe only because of call ordering.

Fix: already tracked as 2.14b — pass an explicit user into BookService instead of mutating the session. This review raises its priority.

M3 Untrusted-file parsers, with no dependency auditing in CI Supply chain

smalot/pdfparser, kiwilan/php-archive (which shells out to unrar), ZipArchive and client-side epubjs ^0.3.93 all parse attacker-supplied files. epub.js is effectively unmaintained.

CI runs npm ci --no-audit and never runs composer audit. There is no static analysis at all.

Fix: add composer audit and npm audit to ci.yml, plus psalm — closing the deferred 4.12.

M4 Internal exception text returned to clients Info leak

PageController.php:276, 312, 405, 469 and SettingsController.php:134 return $e->getMessage() in the JSON body. That surfaces absolute filesystem paths and database/driver detail to any authenticated user.

Fix: log the exception, return a generic message. The listener already models this with its \Throwable guard.

M5 No server-side upload validation; filename reaches the filesystem unsanitised Hardening

uploadBook (:181-278) validates only the publication year. Extension filtering is browser-only (UploadModal.vue:132-135); SUPPORTED_EXTENSIONS gates indexing, never upload. No size cap in app code.

The raw $originalFilename reaches newFile() (:209-210) and is concatenated into a move() target (:260) without passing through FilenameService::sanitizeFilename unless auto-rename happens to be on — so core’s path validation is the only thing standing there. That helper is also incomplete: it strips shell-hostile characters but not leading dots, .., or control bytes, and its substr can cut mid-UTF-8 (FilenameService.php:57-72).

Bounded impact — a user can already write anything to their own storage over WebDAV, so this is contract honesty and defence in depth, not privilege escalation. On exception, the extract-metadata temp file also leaks into the user’s folder root (:298-311).

Fix: validate against SUPPORTED_EXTENSIONS plus a size cap server-side, and always route the filename through the sanitiser.

M6 The library folder setting is written with zero validation Amplifies H1

SettingsController::setFolder (:54-82) writes whatever string arrives straight to config. It never checks that the value is non-empty, that it exists, or that it is a folder rather than a file.

An empty value makes $userFolder->get('') resolve to the user’s root — at which point every listing recursively scans and parses the user’s entire Nextcloud storage, on every request. That is H1b with the brakes off. The value is also interpolated into path matching as strpos($path, "/files/$folderName/") (FileCreationListener.php:86), which wants a traversal check on this Nextcloud version.

Separately: any change silently fires clearLibraryMetadata() (:71), so a typo discards the index.

Fix: reject empty values, resolve the path and confirm it is a folder inside the user folder before persisting.

Reviewed, and fine

What the review cleared

Recording these explicitly so they are not re-litigated later, and so the one load-bearing assumption in the reader is written down where a future change will trip over it.

The new EPUB reader is not a vulnerability

An in-browser reader that renders attacker-authored XHTML inside the Nextcloud origin is exactly the shape of a stored-XSS-to-account-takeover bug. This one is built correctly — but by a chain of three independent controls, and it takes all three: 

epubjs iframe.js:97   iframe.sandbox = "allow-same-origin"   no allow-scripts
ReaderModal.vue:180   allowScriptedContent: false            keeps it that way
PageController:127-133 CSP adds blob: to frame/style/font/
                       image/media — never script-src

Blob-URL documents inherit the parent CSP, so even a sandbox regression would still meet script-src 'self'. External fetches are blocked too, which closes CSS-based exfiltration. The regression to guard: flipping allowScriptedContent to true, or bumping epub.js past a change in its sandbox defaults, converts book content into same-origin script execution. Worth a comment at the call site and a note in the upgrade checklist.

Checked, clean

No injection surface found

  • SQL: every query uses IQueryBuilder with createNamedParameter. No concatenated SQL anywhere in lib/.
  • ORDER BY is allow-listed through a switch (BookService.php:127-141) — no sort-key injection.
  • Dangerous primitives: no exec, eval, unserialize, or outbound HTTP in lib/.
  • Frontend: no v-html, no innerHTML. templates/page.php is a bare mount div with no interpolation.

Checked, correct

Authorisation holds

  • Ownership is enforced via getUserFolder($uid)->getById($id) — a cross-user file id returns an empty array, so it 404s. Every table touch carries AND user_id = <session uid>.
  • CSRF is enforced on all writers; #[NoCSRFRequired] survives only on readers.
  • OPDS auth delegates to logClientIn(), so app passwords, LDAP and 2FA all work — the correct pattern.
  • No secrets committed. Every test123/admin hit is dev or CI scaffolding. getKoreaderPassword returns only has_password.

Explicitly not findings

The unauthenticated /sync/healthcheck is required by the kosync protocol and returns a static string — it reveals only that the app is installed. And the double htmlspecialchars in the facet feeds (OpdsController.php:594, 652, 711, 770, 829 against :222) is a real bug that puts &amp;amp; in published feeds — but it is a correctness defect, not a security one. Over-escaping never was the dangerous direction.

Order of work

Cheapest thing that buys the most, first

Only the first step gates public deployment. The rest is defence in depth and can land incrementally.

Step 1

Rate-limit, and bound the auto-index

#[UserRateLimit]/#[AnonRateLimit] on upload, extract-metadata, batch-rename, bookFile and the OPDS feeds; cap or defer tryAutoIndex; demote the DocumentHashGenerator info logs to debug. Closes H1 and most of L5. This is the deployment gate.

Step 2

Stop leaking internals, validate inputs

Generic client-facing errors (M4); server-side upload allow-list, size cap and filename sanitising (M5); reject empty and non-folder library paths (M6). All small, all local.

Step 3

Close the CI gap

composer audit, npm audit and psalm in ci.yml (M3) — which also finally closes the long-deferred 4.12. Cheapest lasting win in the list, because it keeps working after this review is stale.

Step 4

Rework the sync credential and the session hack

Salted hash plus a server-side length floor (M1), then drop IUserSession::setUser() in favour of an explicit user parameter (M2 / 2.14b). Both touch the auth path, so they want the integration suites green on either side and are best done together, last.

Step 5

The L-series

Header escaping, LIBXML_NONET, OPDS throttle semantics, constant-time user lookup, document-hash validation. Mechanical.

Side finding

tasks.md no longer describes the code

The second question asked was whether everything is implemented. Substantially yes — the Nextcloud 34 modernisation is done, and the five items marked open really are open (2.14b, 2.21b, 2.25, 4.12, 6.6). But the file has drifted in both directions, which makes it unsafe to read as status.

Not a security bug — but it loses user data

Chasing whether a job could be triggered on demand turned up a defect in the 2.24 background-job change. A web-UI upload extracts metadata synchronously (PageController.php:214, 267) — but the file listener has already queued ExtractMetadataJob for the same file id, and indexFile() has no state guard: 

upload  → markFilePending()      indexing_state = pending
        → jobList->add(ExtractMetadataJob, fileId)
        → storeBookMetadata()     writes the user's typed title/author
                                  but never clears indexing_state

+5 min  → cron → indexFile() → updateFileMetadata()
          BookService.php:462-484   SET every column = re-extracted value

Two visible symptoms: the book claims to be “still processing” forever after a web upload, and whatever the user typed into the upload form is silently replaced by the file’s embedded metadata on the next cron run. Scope of evidence: the pending → done transition and the re-extraction were confirmed live on the dev stack (a stuck book went from a filename-derived title to Brave New World / Aldous Huxley once the worker ran); the overwrite of *user-typed* fields is read from updateFileMetadata()’s unconditional SET list, not separately reproduced. Tracked as 8.1, with a regression test. Fix: skip rows already STATE_DONE in indexFile(), and let the upload path mark itself done.

Related, and the reason this went unnoticed: the dev stack has no cron service at all (compose.yaml), so the queue never drains and folder-drop uploads stay pending forever. The pipeline is correct; nothing was running it. Tracked as 9.1–9.5.
