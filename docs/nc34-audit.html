Compatibility audit · koreader_companion v1.2.4 · 10 Aug 2026

It isn’t out of date. It’s already broken.

The app declares support for Nextcloud 30–31. The question was what it would take to reach Nextcloud 34. The answer is that four separate hard fatals land between 33 and 34 — the library page won’t render, the OPDS feed won’t serve, and the entire frontend is dead JavaScript. Every version claim below was checked against the tagged Nextcloud sources, not from memory.

Blockers

The six things that must change to boot on 34

Each of these is a fatal or a hard refusal, not a warning. Nothing else in the migration matters until they are done.

F1 The library page fatals while rendering Removed in 34.0.0 The template reaches into private API for the user’s timezone: templates/page.php:139 and :165 call \OC::$server->getConfig() and ->getUserSession(). Fires only for books that have sync progress, so an empty library may look fine — which is how this hides.
F2 The OPDS feed fatals — no reader can connect Removed in 34.0.0 Four calls to \OC::$server->getURLGenerator() in OpdsController.php:352, 357, 362, 377. IServerContainer went from 64 public getters at v31 to 32 at v32 to three at v34, and \OC\Server has no __call fallback.
F3 The entire frontend is dead JavaScript Removed in 33.0.0 101 jQuery call sites across js/koreader.js (1,363 lines). jquery is present in the server’s package.json at v31 and v32 and absent from v33 onward, alongside jQuery UI, Backbone and Handlebars. Nothing interactive survives — navigation, search, sort, upload, settings.
F4 Every success and error toast is a no-op Removed in 34.0.0 26 calls to OC.Notification.showTemporary. core/src/OC/notification.js resolves at v31 through v33 and 404s at v34.0.0. The user gets silence instead of feedback.
F5 The app cannot be installed at all n/a appinfo/info.xml:20 declares max-version="31", so occ app:enable refuses on 32 and up — and any later core upgrade will auto-disable the app again.
F6 The declared PHP floor is wrong in three directions n/a composer.json says "php": ">=8.0", but its own dependency kiwilan/php-archive requires ^8.1, Nextcloud 33+ requires 8.2, and the NC 34 image ships PHP 8.5. The release workflow meanwhile pins 8.1.

What you actually get

Covers, progress, and the UI you haven’t seen yet

You asked what this app looks like. Short answer: a dense eleven-column text table, no cover art anywhere, but reading progress genuinely does show up. The cover situation is the interesting one — the extraction code exists and works, and nothing ever displays it.

Today

Book covers: extracted, then thrown away

  • EPUB and CBR covers work. EPUB parses the OPF <meta name="cover">, then cover-image, then guesses filenames. CBR takes the first image alphabetically.
  • PDF and MOBI return HTTP 501 — hardcoded, no rendering at all.
  • Nothing is ever displayed. There is no <img> in the template and no cover CSS. The only endpoint is /opds/books/{id}/thumb, which is Basic-auth only — unreachable from the logged-in web session. That single fact is why you see no covers.
  • Thumbnails are regenerated on every single request, never cached. A cover_image column exists in the database and is never read or written.
  • OPDS advertises a thumbnail link even for PDF, so readers show broken art.

Proposed

Hand covers to Nextcloud’s own preview system

  • Register EPUB and CBR as preview providers (registerPreviewProvider(), available since NC 23) instead of running a bespoke endpoint.
  • The frontend then just uses /core/preview?fileId=…. The Basic-auth limitation disappears, and covers get cached by the platform.
  • PDF needs no new code. Core already ships an OC\Preview\PDF provider; it is disabled by default for performance and privacy, so this becomes a documented admin toggle plus a ghostscript install — which, notably, the official Nextcloud image does not include.
  • Covers start appearing in the Files app for free.
  • Degrade to a placeholder when the provider is off. Never a 500.

Reading progress — this part already works

Shown today

  • A mini progress bar per row with a rounded percentage, plus the device name truncated to 8 characters.
  • A “Last Sync” date converted into the user’s own Nextcloud timezone, with a full timestamp on hover: “42.7% complete on kobo_cla… (last sync: …)”.
  • Backed by oc_koreader_sync_progress — note the project’s own CLAUDE.md documents this table under the wrong name.

Missing or broken

  • The actual reading position is fetched from the database and then discarded. No “page 123 of 400”, no chapter.
  • Only the single most recent device is shown — no per-device breakdown, no “currently reading” view.
  • Rows appended by infinite scroll use different CSS classes and different date formatting than server-rendered ones, so the table visibly changes character after the first 50 books.
  • An empty library breaks the page. With no books, the search box and table are never rendered, so the scroll observer gives up and the view cannot recover without a reload.
  • No download link, no read-in-browser, no reset-progress, no bulk select. The only per-book action is “edit metadata”.
  • Sorting is client-side over whatever rows happen to be in the DOM. The backend supports real sorting; the UI never asks for it.

Independent of any version

Security and correctness

These were not part of the compatibility question, but they are real and worth fixing in the same pass.

S1 The KOReader sync API is an unthrottled credential oracle Security Sync endpoints are marked public and compare a bare MD5 of the password with no brute-force protection, then call IUserSession::setUser() to fake a login (KoreaderController.php:195, 338). The OPDS controller already injects a throttler — this one simply doesn’t.
S2 Ten state-changing endpoints have CSRF protection switched off Security Five PageController writers (including upload, delete and set-sync-password) and five SettingsController writers carry @NoCSRFRequired — while the JavaScript already sends the token. The protection would pass if enabled; disabling it is the entire hole.
S3 Retracted: the schema installs fine on MySQL Disproven This was published as a blocker — meta_path_idx indexes a 4,000-character column, and InnoDB caps an index key at 3,072 bytes, so ERROR 1071 looked inevitable. It does not happen. Tested on a real MariaDB 11 install: the app enables cleanly and MariaDB silently narrows the index to file_path(768). The residual issue is far milder — the index covers only the first 768 characters, which is ample for real Nextcloud paths. No fix warranted. Assumed from the byte arithmetic; only running it settled the question.
S4 A catch block references a class that does not exist Correctness OpdsController.php:65 catches \OC\Security\Throttle\MaxDelayReached. The real class lives under Bruteforce, not Throttle — so the catch never matches and a throttled client gets a 500 instead of a 429.
S5 Migrations reach directly into core tables Correctness Raw SELECT/DELETE against oc_preferences, oc_appconfig and oc_users, which breaks against NC 31+ typed and lazy config. Separately, a migration issued DROP TABLE with a hardcoded oc_ prefix and MySQL backticks. Confirmed on both engines: Postgres rejects the backticks outright and the table survived on Postgres and MariaDB, so that cleanup had never once run. Five indexes duplicating another index on the same columns were also confirmed on a live MariaDB schema. Both now fixed via a declarative ISchemaWrapper migration.
S6 The navigation entry is registered twice Hygiene Once in info.xml and again in Application::boot(), both with the same id.

Found only by running it

Three things the static read could not have told us, all surfaced by booting the app on 34:

R1 Turning on debug silently breaks all metadata extraction Runtime With debug=true, Nextcloud enables its dirty table reads assertion. The upload listener reads oc_filecache inside the very transaction the upload just wrote to, so it throws on every WebDAV PUT and the metadata table stays empty — with no visible error for the user. It works today only because nobody develops with debug on.
R2 Two more dead database columns Runtime binary_hash and filename_hash in oc_koreader_metadata are always NULL; the real hashes live in oc_koreader_hash_mapping. Same story as cover_image.
R3 The test suite disagreed with the code — and the code was right Corrected Three assertions demanded a application/vnd.koreader.v1+json response. But v1.2.3 deliberately changed that to application/json, because real KOReader clients otherwise fail to pull progress and report “No progress found for this document” (issue #4, upstream koreader/koreader#13539). The stale expectation was moved, not the header — the more spec-looking value is the broken one.
R4 A “dead” autoload line that is load-bearing Trap Application::__construct() manually requires vendor/autoload.php, which looks redundant because Nextcloud registers an app autoloader. It is not: that autoloader covers the app’s own OCA\* namespace, not third-party PSR-4 packages. Removing it makes Kiwilan\Archive\Archive unresolvable, and because the extractor catches Throwable, EPUB and PDF metadata silently degrade to filename parsing — titles become “dev-stack-handbook” and authors “Unknown”, with only an info-level log line. Found by removing it, then noticing the extracted metadata differed between the Postgres and MariaDB stacks. Now restored with a comment saying so.
R5 The sync response was missing two fields the reference server sends Protocol GET /sync/syncs/progress/{document} returned only progress, percentage, device and device_id. The reference kosync server also returns document and timestamp, and both matter: omitting document is precisely what broke pulls in Readest on iOS against custom servers (readest#5065, worked around client-side in v0.11.20), and without timestamp a client cannot tell whether the server’s progress is newer than its own — conflict resolution collapses to last-writer-wins, so a device that has been closed for a week can silently overwrite newer progress. Both now returned; found while checking which iOS apps can actually talk to this server.
Things that look outdated but are actually fine — don’t spend effort here

Several plausible-looking concerns turned out to be non-issues on 34, which matters as much as the real findings:

  • OC.dialogs.filepicker and FILEPICKER_TYPE_CHOOSE still exist in v34 as a legacy wrapper. Deprecated since 27.1, not removed. Migrate for hygiene, not urgency.
  • Array-based routes in appinfo/routes.php remain fully supported. Only App::registerRoutes was removed.
  • Docblock annotations such as @NoAdminRequired still function on 34. All 41 controller methods should move to PHP attributes, but that is not what is breaking anything.
  • \OC::$server->get() still works, because IServerContainer extends PSR-11 ContainerInterface.
  • \OCP\Util::humanFileSize() survives; it was \OC_Helper::humanFileSize that went in 32.
  • IQueryBuilder::execute() was removed in 33 — and this app has zero call sites. A genuine near-miss.
  • smalot/pdfparser is used, just never declared — it arrives transitively via kiwilan/php-archive. It should be an explicit dependency, but the code is correct.

Sequenced by dependency, not by size

Proposed route to 34/35

Phases 0 and 1 deliberately come first because they do not require the app to work. Provisioning runs entirely through occ and WebDAV, so the dev stack comes up green while the app is thoroughly broken — giving you somewhere to actually watch the fatals happen.

Phase 0

Tooling

Jujutsu instructions for the agent, with git retained as the fallback for non-jj repos. Outside the repo; no code impact.

Phase 1

A local stack that actually starts

Pinned nextcloud:34.0.2-apache with PostgreSQL 17 and a healthcheck gate, replacing the current unpinned nextcloud:stable whose only app mount is commented out and points at a dead path. The app bind-mounts into custom_apps/ — the one directory the image’s first-boot rsync is guaranteed to leave alone — so PHP, JS and CSS edits are live with no docker cp. Composer runs in a container, so no host PHP is needed. Seeding goes through WebDAV, because the metadata listeners fire on Nextcloud’s write events and occ files:scan does not trigger them. A second profile on NC 31 makes “worked before, breaks now” a one-command comparison. The macOS test scripts get fixed too: today they need md5sum and GNU grep -P, neither of which exists here.

Phase 2

Unblock the backend

Kill F1, F2, F5 and F6; inject the services that were being fetched from the service locator; move all 41 controller methods to PHP attributes and drop the CSRF exemptions while in there; add brute-force protection to the sync API; replace the deprecated config interface; and fix the migrations. Verified by app:enable succeeding without --force and by running migrations against both Postgres and MySQL.

Phase 3

Covers through the preview system

Move EPUB and CBR extraction into registered preview providers, gain PDF from core, delete the bespoke thumbnail path and the unused database column.

Phase 4

Vue frontend

Resolves F3 and F4 together, because they are one job. Pinned to exactly the dependency set NC 34.0.2 ships itself — @nextcloud/vue 9.8, vite 7, vue 3.5 — so there is no version guessing. Moving to initial-state hydration collapses the current render-then-refetch pattern into one path, which incidentally fixes both the empty-library dead-end and the markup divergence after the first scroll page. The library becomes a cover grid, and the backend’s existing sort parameter finally gets used.

Method. Version claims were verified by fetching nextcloud/server at tags v30.0.0, v31.0.0, v32.0.0, v33.0.0, v34.0.0 and v34.0.2 and diffing the relevant files — lib/public/IServerContainer.php, lib/private/Server.php, core/src/OC/* and package.json — rather than relying on release notes or recollection. Call-site counts come from the working tree at b96d432 (v1.2.4). Where the documentation and the source disagreed, the source won; several first-pass conclusions were discarded on that basis and now appear in the “actually fine” list. One finding published in the first version of this page — S3, “the schema cannot be installed on MySQL” — was retracted after testing it on a real MariaDB 11 install. The byte arithmetic was right and the conclusion was wrong; MariaDB narrows the index instead of refusing it. It is left visible above rather than quietly deleted.

Open questions worth deciding before Phase 4: whether the OPDS facet feeds need to keep their current URL shape, and whether MOBI is worth supporting at all given it has neither cover extraction nor a preview provider.
